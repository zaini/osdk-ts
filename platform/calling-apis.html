Call platform APIs

The calling convention for @osdk/foundry functions, including argument order, pagination, errors, binary responses, and preview endpoints.

Foundry docsAPI getting started

Every Platform SDK function takes the client first, then the endpoint's path, body, query, and header arguments, in that order. This page covers that convention and how to handle pagination, errors, binary content, and preview endpoints.

Import a namespace

Each package exports one namespace per resource, named in the plural: Users, Groups, Datasets, Files, MediaSets. Each function in a namespace maps to one REST endpoint.

Request and response types, such as User, Group, and ListUsersResponse, are exported by name from the same package. Identifier types such as UserId and PageToken are strings, so plain string values work wherever they are expected.

Argument order

After the client, a function takes up to four groups of arguments, always in this order:

PositionArgumentExample
1The clientclient
2Path parameters, one positional argument each, in URL orderdatasetRid, filePath
3The request body, for POST and PUT endpoints{ where: { type: "queryString", value: "jane" } }
4Query parameters, as one object{ pageSize: 100, preview: true }
5Header parameters, as one object{ ReadToken: token }

A function only takes the groups its endpoint has:

When a function has optional query parameters and you need to pass headers, pass undefined or an object for the query parameters first. Your editor shows the parameter names, such as $queryParams and $headerParams, on hover.

Responses

Endpoint returnsThe function resolves to
JSONThe parsed body, typed, such as User or ListGroupsResponse.
No content (204)undefined. The return type is Promise<void>.
Binary contentThe Response. Read it with .blob(), .arrayBuffer(), .text(), or .body.

Upload endpoints such as Files.upload and MediaSets.upload take the bytes as a Blob. A File from an <input type="file"> is a Blob, so you can pass it directly.

Paginate

List and search endpoints return one page at a time as { data, nextPageToken }. Pass nextPageToken back as pageToken to get the next page. The last page has no nextPageToken.

ParameterTypeDescription
pageSizenumberPreferred page size. The server can return more or fewer items, and some endpoints cap it.
pageTokenstringToken from the previous page. Omit it for the first page.

For GET endpoints, such as Users.list, these are query parameters. For POST endpoints, such as Users.search, they go in the body.

Handle errors

A failed call rejects with a PalantirApiError, exported from @osdk/client. This includes network failures and error responses that are not JSON; those have no errorName, and the underlying error is on cause. If the token provider itself throws, the call rejects with a plain Error.

FieldTypeDescription
messagestringThe server's message, or Failed to fetch <status> <statusText>.
errorNamestring | undefinedStable identifier, such as UserNotFound or ApiFeaturePreviewUsageOnly. Switch on this.
errorCodestring | undefinedCategory, such as NOT_FOUND, PERMISSION_DENIED, INVALID_ARGUMENT, or CONFLICT.
errorDescriptionstring | undefinedHuman-readable description.
statusCodenumber | undefinedHTTP status.
errorInstanceIdstring | undefinedServer-side ID for this occurrence. Include it in support requests.
parametersobject | undefinedContext for the error, such as { userId }.

Each package exports a type for every error it can return, with the exact errorName, errorCode, and parameters. Import them to see what to expect:

Shared errors, such as ApiFeaturePreviewUsageOnly, InvalidPageToken, and ApiUsageDenied, are exported from @osdk/foundry.core.

The client retries 429 and 503 responses up to three times before rejecting. Other errors reject immediately.
