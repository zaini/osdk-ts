FilterList

FilterList renders filter controls for an OSDK object type or object set, backed by aggregations, and reports the combined where clause or filtered object set.

Prerequisites

Before using FilterList, make sure you have completed the library setup described in Prerequisites, including:

  • Installing the required dependencies
  • Wrapping your app with OsdkProvider
  • Adding the CSS imports

Import

Basic Usage

@my-app/sdk is a placeholder for your generated SDK package. ./client is the file in your app where you exported the OSDK client returned by createClient(...). Replace both with the actual paths in your project.

The simplest way to use FilterList is with an objectSet and a few filter definitions:

How LINKED_PROPERTY filters

Like HAS_LINK, a LINKED_PROPERTY filter applies only through onEffectiveObjectSet — it never appears in onFilterClauseChanged. FilterList derives a count of the linked objects matching the filter (withProperties({ …: (base) => base.pivotTo(linkName).where(...).aggregate("$count") })) and keeps the rows whose count is above zero:

reverseLinkName is deprecated: filtering counts linked objects instead of pivoting back to the source type, so no back-link is needed. Definitions that still pass it keep working — the value is ignored.

Reading everything from one callback

onFilterListChanged reports the state the list mounted with and every change after it — a filter set, a filter removed, or a reset — as an event with a reason (what happened) and a snapshot (everything derived from the resulting state), so you don't need to wire up onFilterStateChanged, onFilterClauseChanged and onEffectiveObjectSet separately and reconcile their firings:

event.reason.typeExtra fieldsFires when
"FILTER_LIST_INITIALIZED"—The list mounted, once, before any interaction
"FILTER_STATE_CHANGED"filterKey, newStateThe user changed a filter's value
"FILTER_REMOVED"filterKeyA filter was removed from the list
"FILTER_LIST_RESET"—The reset button restored the mount state

filteredObjectSet is undefined when no objectSet prop is supplied.

"FILTER_LIST_INITIALIZED" reports the state seeded from defaultFilterStates and from each definition's defaultFilterState, so the initial clause and filtered ObjectSet arrive without waiting for a first interaction. If you only care about the current state and not what caused it, ignore reason — every snapshot carries the full filterClause and filteredObjectSet:

Changes are reported as they happen, with no debounce, so an analytics handler sees every distinct interaction. Free-text and range inputs debounce their own keystrokes, so typing reports once per pause rather than once per character. If you need coarser batching than that — one network request per burst, say — debounce your own handler.

Collapsible Panel

The collapse control is available by default and FilterList owns the collapsed state, so collapsing works with no wiring at all:

Start collapsed with defaultCollapsed. onCollapsedChange fires in both modes; in uncontrolled mode it is purely a listener on top of the built-in behavior, so the panel keeps collapsing and expanding on its own. Use it when the surrounding layout needs to react:

To own the state yourself, pass collapsed instead of defaultCollapsed. That switches the feature into controlled mode: the prop is the source of truth, the component keeps no internal state, and the panel only moves when you re-render with a new value in response to onCollapsedChange. If both are supplied, collapsed wins.

onCollapsedChange is only an event listener — it never enables the control and never takes over the state. Availability is governed by enableCollapse alone.

Pass enableCollapse={false} to pin the panel open and remove the control entirely; collapsed and defaultCollapsed are then ignored.

Best Practices

  • Memoize filterDefinitions -- define the array outside the component or wrap in useMemo to avoid unnecessary re-renders
  • Persist filter state with defaultFilterStates -- read changes out via onFilterStateChanged, key them with the exported getFilterKey(definition), and pass them back through defaultFilterStates to rehydrate after navigation. serializeFilterStates / deserializeFilterStates handle the Date round-trip for you
  • Use objectSet constraints to scope filter values -- pass a prefiltered objectSet (e.g. client(Employee).where(...)) so filter dropdowns only show relevant values
  • Keep filter lists focused -- show 3-8 filters; too many filters overwhelm users
  • Use addFilterMode="uncontrolled" for progressive disclosure -- start with a few visible filters and let users add more as needed
